# Authentication setup (local pilot)

Provision credentials and HTTPS before exposing this release. Credential-bearing runtime files are excluded from the current source tree. The login password and exposed Kitchen tunnel secret were rotated on 12 November 2026; historical copies remain in Git and must not be reused. Do not put new secrets in the repository. See `DEPLOYMENT_RUNBOOK.md` before updating an existing installation: preserve host configuration outside the checkout before any Git update that removes formerly tracked runtime files.

Set these environment variables outside the checkout, in a protected service environment:

- `KITCHEN_USER`: the owner's username, up to 256 characters.
- `KITCHEN_PASSWORD_HASH`: initial verifier, when no credential store is configured. Run `python hash_password.py` interactively on a trusted machine and provision its output privately. Do not pass passwords as command-line arguments or commit the verifier. Use a strong unique password.
- `KITCHEN_CREDENTIAL_STORE`: optional absolute POSIX path outside the checkout to an existing protected verifier file. This must be configured and provisioned before the owner can change the password in Help. If set, the file is authoritative; missing, malformed, inaccessible or unsafe storage causes all API authentication to fail closed, with no fallback to the environment verifier.
- `KITCHEN_ORIGIN`: exact browser HTTPS origin, for example `https://manager.example.com` (no trailing slash or path). All state-changing requests require this Origin and JSON content type.

Missing or invalid settings cause API requests to fail closed with 503. Cookies require HTTPS, including local browser checks. The hash uses PBKDF2-HMAC-SHA256 with 600,000 iterations and a random salt. A successful password change invalidates every session and requires a new sign-in. Use at least 15 characters; password managers and paste are supported. A small offline list blocks a few common passwords and repeated single characters, but this is not comprehensive breached-password screening. The password is not sent to the chat agent.

This is a **single-process pilot**: random server-side sessions expire after eight hours and are lost on restart. A maximum of 256 sessions and 1,024 login-client entries are held in memory; login attempts are limited to five per client per five minutes. These limits are per process, not distributed or durable. Do not run multiple workers without replacing both stores with shared, suitably protected storage. The backend uses the direct client address; it must not trust forwarded headers from clients. `python backend.py` explicitly disables Uvicorn proxy-header handling. If launching Uvicorn separately, use `--no-proxy-headers`. Behind a tunnel, clients may share one direct address and the limit may affect all users; determine a trusted proxy and enforce a suitable limit at the edge before deployment. Never trust a forwarded address without explicit trusted-proxy configuration.

Confirm the actual manager origin, HTTPS termination, routing, access controls and Hermes profile permissions before release. Limit request sizes at the edge as well. The chat agent still needs separate capability isolation and reliability work; authentication does not constrain its tools. Session storage and throttles do not provide multi-process coordination or resistance to a distributed login attack.

For local automated checks, install `requirements-test.txt` in an isolated environment and run `python -m unittest discover -s tests -v`. Tests must mock the agent and use synthetic data and credentials.

## Provisioning password changes

Before deploying this feature, an operator must prepare an owner-only directory (mode 0700) outside the checkout and web-served paths, and an owner-only regular verifier file (mode 0600) in that directory. The service user must own both. The path and its parent chain must contain no symlinks; ancestors must be owned by root or the service user and not writable by other users, except root-owned sticky directories such as `/tmp`. The file must not be hard-linked. Use an absolute path in `KITCHEN_CREDENTIAL_STORE`. On non-POSIX systems protected storage fails closed. These checks and atomic replacement are intended for the documented single-process Linux pilot.

For an existing installation, provision the file with the **current verifier** from the existing protected environment, without printing, logging, copying into source control, or exposing it to another user. Alternatively arrange a private credential reset and generate a verifier with `hash_password.py`, redirecting its output directly into a newly created owner-only file; the operator must use the same new password to sign in. Never overwrite an existing verifier casually. Verify ownership, permissions, regular-file status, parent path, and backup before configuring the environment variable; then verify login and change in an isolated test environment before enabling live traffic. Keep old environment settings outside the checkout.

The service atomically writes a fresh verifier and syncs it and its directory, then invalidates every session. Current-password failures are limited account-wide to five per five minutes in this process. This is in-memory and resets on restart; it is not a distributed rate limit. Locks, session state and attempt counters are not shared across workers. Multiple workers are unsupported; do not edit or replace the verifier concurrently with the service.

Back up the protected verifier and recovery procedure securely outside the repository. If the store is missing, corrupt, unsafe or the password is forgotten, close public access and have an authorized operator restore a protected valid verifier or reset it with `hash_password.py` and a private new password. Restart the service to invalidate its in-memory sessions and verify access before reopening. Never fall back silently to the old environment hash. If an update reports an uncertain outcome, sign in with the new password first; the previous password may still work if the write did not complete.
