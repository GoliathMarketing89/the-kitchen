# Manager authentication release and rollback

This is an operator runbook, not evidence of a deployment. The configured tunnel hostname is `manager.freshlymade.net`; the checked-in backend unit invokes Python from a Hermes-managed environment. Verify the live host, unit scope and routing before applying these instructions. Do not print credentials, verifier, cookies or configuration contents into terminals captured by logs, issue trackers or chat.

## Prepare

1. Identify the exact reviewed commit and transfer only the intended code: `backend.py`, `static/app.js`, `static/index.html`, `hash_password.py`, `requirements.txt` and `AUTH_SETUP.md`. Do not copy `.git`, `backend.env`, `.cloudflared`, business records, or an entire working tree. Check that staged Git paths do not include tracked secret-bearing files. Existing tracked secrets and history require separate credential rotation and remediation; `.gitignore` alone cannot remove them from history.
2. Confirm a Python 3.11 or newer interpreter is available. Starlette 1.10.0 requires 3.11; the other pinned runtime packages require at least 3.10. Install and verify pinned dependencies in a separate restricted virtual environment, not the existing Hermes environment. Check `pip check`, imports and versions. Ensure that the production service uses exactly one worker and, if its executable must change, review a narrow systemd override. Preserve the old executable and unit configuration for recovery. `backend.py` disables Uvicorn's proxy-header trust; a separate Uvicorn invocation must use `--no-proxy-headers`.
3. Provision `KITCHEN_USER`, `KITCHEN_PASSWORD_HASH`, and `KITCHEN_ORIGIN` in a protected environment file outside the checkout. Use `hash_password.py` interactively on a trusted host and provision its result privately; use the exact origin `https://manager.freshlymade.net` if live routing confirms it. Ensure the service actually reads the protected file, with no conflicting values later in its environment configuration. Configuration errors cause API requests to return 503. Retain the current environment file without displaying its contents and do not overwrite it blindly; it may contain settings needed by the existing service or Hermes.
4. Establish who can stop/restart the tunnel and backend and where the private backup is stored. Alert users to a brief interruption. Stop new requests at the tunnel, then drain or stop in-flight Hermes jobs before taking a consistent backup; a stopped HTTP service alone does not prove a spawned job has completed. Confirm no record writer remains active.
5. Under a restrictive umask and permissions, create a timestamped private backup outside the served and repository directories. Preserve the existing backend and manager UI, actual service unit and overrides, environment configuration, and business data including `menu.json`, `recipes.json`, `sales.json`, and `state.json`; inventory any additional files used by the installed Hermes profile. Verify backup readability and practice restoring a copy to a separate directory. Limit access and retention because backups can contain credentials and business records. Do not place secrets in source control.

## Release and verify

1. Keep the tunnel closed. Copy only the reviewed code files and point the single backend service at the verified runtime and protected environment. Avoid changing menu data, tunnel credentials, DNS, or the public menu. Restart the backend in its confirmed systemd scope and check service health without dumping its environment. The process runs as the existing service user; confirm it can read the configuration, code and records.
2. Open the tunnel and check HTTPS from an independent client. Verify `/` loads the manager and `/api/session`, `/api/status`, `/api/recipes`, `/api/shopping-list`, `/api/profit` return 401 without a cookie. A JSON POST to `/api/chat` with the exact Origin must return 401 without running Hermes. Verify `/docs` and `/openapi.json` are unavailable, and a mismatched Origin is rejected. Do not use a real chat request or mutate business data as a health check.
3. Have an authorized owner sign in through the real HTTPS page. Verify the cookie has `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, and no Domain; refresh and confirm the session persists. Log out, then confirm the old session no longer authorizes an API request. Check the real phone browser and retain no password or cookie in the test record. Restart invalidates all sessions. If verification fails, close the tunnel and investigate before reopening.

## Rollback and data recovery

Stop new traffic and wait for active record-writing jobs to finish. Preserve the *current* business records and service logs privately before changing anything. Restore the previous code and service configuration independently of data; verify the prior runtime and environment are still available. **The previous backend does not enforce API authentication. Do not reopen its public tunnel** unless an independently verified access control protects every private endpoint. Prefer leaving the manager offline while fixing or reapplying the secured release.

A code rollback must not replace records created since the backup. Restore data only for a diagnosed data-loss event, after comparing the current records and backup, preserving both, and obtaining the appropriate business authorization. Verify the selected restore in isolation first. Reopen access only after authentication and routing are verified, then record the release or incident and any follow-up credential rotation.

The pilot stores sessions and login throttles in one process and loses both on restart. The tunnel can make all users appear to share one direct client address, so five attempts in five minutes may temporarily block everyone. A distributed edge rate limit and a trusted client-address design require separate verification; never trust arbitrary forwarded headers. Authentication alone does not limit the Hermes profile's permissions or establish safe backups.
